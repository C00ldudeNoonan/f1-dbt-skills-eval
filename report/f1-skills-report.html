Experiment report · F1 dbt project · 17 agent runs

Do dbt skills matter?

We had Opus, Sonnet, and Haiku build and maintain a Formula 1 dbt project on Snowflake from scratch, with and without the dbt agent skills, through up to 12 tickets each. Every model was graded against an answer key after the harness injected new data, broke the vendor feed, and planted bugs.

Oct 20–21, 2026 · dbt v2.0.6 on Snowflake · Claude app (Code tab), Auto mode · dbt-agent-skills @ ef57108

Short answer

For correctness, no. For code quality, a little, and less as the model gets stronger. Every model built correct projects without skills. Of the 6 runs that missed answer-key checks, 5 had skills available or forced. What caused misses was a single early mistake that later tickets never fixed, not a lack of dbt knowledge.

Skills did nudge blind code-review scores up on the 7-ticket suite (every skills arm beat its model's no-skills run), but the effect shrank on the harder 12-ticket suite and sits near the reviewer's own run-to-run noise (about 0.2 points). Agents also rarely opened the skills unless told to: runs with skills available read 0–4 skill files across an entire suite, mostly for the Semantic Layer and for contracts and versioning.

What we found

  • Correctness was high everywhere. 11 of 17 runs passed every answer-key check across every ticket. The lowest score (Sonnet with skills available, 61% on the 12-ticket suite) came from restoring a stale backup during a bug fix, which silently reverted 215 corrected lap times and cascaded into four models.
  • Forcing skills made small models busier, not more correct. Haiku with skills forced used about 1.6× the output tokens and 1.5× the dbt calls of Haiku without skills on the first suite, and it was the only first-suite run to miss checks: it read "career starts" as races started instead of the specified "Grands Prix entered".
  • Model size mattered more than skills. On the first suite, Opus code scored 4.5–4.6 while Sonnet and Haiku scored 3.5–4.0. On the harder suite the gap closed: every model wrote production-grade projects (3.9–4.7).
  • The most common real defect was a brittle test, evenly split across arms. Nine runs (three in each arm) wrote a test that hard-codes today's answers (a list of world champions ending in 2023, or fixed career totals). When the harness delivered the final 2024 race, those tests failed the build even though the data was right.
  • Hard engineering tickets were solved almost universally. All 9 runs on the harder suite passed slim CI, matched all 41 drivers and 167 sessions of an unfamiliar second vendor feed, and found the hidden duplicate standings rows nobody asked them about.

Ticket by ticket

Greenfield build
Every trap caught

All runs handled the literal \N nulls, lap times stored as text, red-flag pit stops, and pre-1991 dropped scores (official standings, not summed points). One miss: Haiku with skills forced misread a column definition.

Incremental + corrections
Lookback windows everywhere

Every run reprocessed the two most recent races so reissued lap times flowed through without a full refresh.

Late-arriving drivers
Two runs skipped the placeholder

All kept the reserve driver's result. Sonnet with skills available and Haiku with skills forced didn't add the placeholder row to dim_drivers that the ticket asked for.

Vendor drift
Fixed, sometimes slowly

Every run recovered from renamed columns, a renamed table, and DD/MM/YYYY dates. Two runs added drift guards that made builds 10× slower before they noticed.

Planted bugs
Hidden bug found by all

All found the duplicated Ferrari row and, unprompted, the resent standings rows, and added upstream uniqueness tests. One restored a stale backup while fixing it.

Second vendor feed
Automatic matching

All 9 matched every driver (accents, "Alex" Albon) and every session, including the two 2020 races at Spielberg, using dates.

Telemetry at scale
Right watermark, varied cost

8 of 9 runs keyed incrementals on load time and landed the 3-week-late samples correctly. Routine-rebuild scan cost ranged from 0.36× to 12×, mostly driven by full-table tests.

Slim CI
9 of 9 pass

Every ci.sh built exactly the edited model, its downstream models, and new models into the CI schema, deferring the rest to prod.

Vague leadership asks
Defensible, with pushback

Nearly every run measured drivers against teammates rather than raw wins, and noted pit-stop data only starts in 2011. Reviewers scored this 4–5 everywhere.

How much to trust this

  • One run per cell. Each model × arm × suite combination ran once. Treat gaps between individual runs as hints; the pattern across 17 runs is what holds up.
  • Cross-run contamination. The app gives sessions a shared notes folder, and agents used it to trade data findings. 8 runs read other runs' notes, mostly during the first ticket of the 12-ticket suite. We locked the folder once we found it. The table flags each affected run.
  • Prompts were sent as session messages. Agents could tell tickets came from another session, not a person. Two runs needed a human approval for a prod build the app's auto-mode check blocked; these are logged as environment interventions, not nudges. Two runs got one "continue" nudge each.
  • Harness fixes mid-run. Three grader bugs were found and fixed while runs were in flight: an ambiguous podium definition, a telemetry cost query that missed staging views, and a CI probe that read a file some scripts overwrite. Affected tickets were regraded; no agent saw any grade.
  • Semantic Layer wasn't executed. dbt sl needs a dbt platform connection, so the metrics ticket is graded on definitions only.

What to try next

  • Run 3 or more seeds per cell on the 12-ticket suite with the notes folder locked from the start, to get a real variance estimate.
  • Test skills that target the observed failure modes: one on writing future-proof tests, and one on verifying a restore before trusting it.
  • Add the Wizard arms (Wizard as shipped, and Wizard driving Opus) so the comparison covers harness, not just skills.
